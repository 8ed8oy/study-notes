# S7 闭卷自测（20 题）

## 模型与执行
### 1. 一次 forward 从 input_ids 到 logits，张量形状怎么变？prefill 和 decode 在哪个维度不同？  
答：input_ids:prefill 为 [Σ S_i]（把各序列的新 token 拼平，即 packed/varlen，边界用 cu_seqlens 记）；decode 为 [B] （S为1）-> embedding:[B, S, H] -> 28层decode:[B, S, H] -> logits:[B, V]（只取每序列最后一位；V 是词表大小，固定）。prefill 和 decode 在 S 维度不同，prefill 是一次性处理整个序列，decode 是逐 token 处理。B=batch_size，S=seq_length，H=hidden_size。
### 2. MHA/GQA/MQA 的 KV 头数差异，如何影响 KV cache 大小和 decode 带宽？  
答：由公式kv_cache = KV = 2(K,V) × layers × kv_heads × head_dim × seq_len × bytes，KV 头数减少会导致 cache 大小减小，从而降低读带宽的需求，而 Q 头数保持不变。验算：2×28×8×128×2048×2 = 235 MB。
### 3. RoPE 作用在 Q/K 还是 V？为什么能编码相对位置？  
答：RoPE 作用在 Q/K 上，RoPE会根据位置将向量进行旋转，使得Q和K的内积带有两个位置间的相对位置信息，内积只依赖相对位移，因此可以编码相对位置。V 不旋转。
### 4. 权重、激活、KV cache 各占什么显存？0.6B、fp16、seq=2048 时 KV 大约多少？——要点：2×L×H_kv×D×S×bytes；你 S2 算过。
答：权重 = 参数量 × 每参数字节数。0.6B 是 0.6×10^9 个参数，fp16/bf16 每参数 2 字节 → 1.2 GB（约 1.12 GiB）。
粗算参数量：embedding V×H ≈ 151936×1024 ≈ 155M；每层 attention q/k/v/o ≈ 6.3M + MLP gate_up/down ≈ 9.4M ≈ 15.7M；×28 层 ≈ 440M；加起来 ≈ 595M ≈ 0.6B（lm_head 与 embedding 共享，不另算）。
激活是临时的，prefill 峰值大致 B×S×H×bytes 的几倍（FlashAttention 不存 S² 矩阵），量级几百 MB。
KV：seq=2048 时 235 MB（见 Q2）。

## 调度与生命周期
### 5. 一次 step() 做哪三件事？prefill 的 step 和 decode 的 step 差在哪？  
答：① Scheduler.schedule() 选出 prefill 或 decode 的序列，prefill序列来自waiting队列，decode序列来自running队列；② model_runner.run() 得到 token_ids；③ Scheduler.postprocess() 更新状态、释放 KV cache、记录输出，若eos则结束。补：只有 prefill 会把 waiting 移到 running；postprocess 不会把 running 序列"放回" running，结束的移除、被抢占的进 waiting。
### 6. waiting/running/finished 怎么转移？preempt 为什么用 appendleft（LIFO）？代价是什么？  
答：waiting -> running: prefill；running -> finished: eos；running -> waiting: preempt。appendleft 是为了减少这条序列反复被抢占的次数，但可能导致某些序列长时间无法执行（饿死）。补：preempt 会释放 KV，恢复时要重新 prefill 整段。
### 7. continuous batching 为什么优于静态 batching？    
答：因为 continuous batching 可以根据每个 step 的 token budget 动态调整 batch 中的序列，避免短序列被长序列拖慢，从而提高整体吞吐量。若静态batching，短序列生成完以后，它的 slot 空着（或 padding 陪跑），直到整批结束，浪费算力。
### 8. chunked prefill 解决什么？为什么它不把序列翻回 WAITING？
答：解决了长序列 prefill 阻塞 decode 的问题；chunked prefill 把长 prompt 切成 ≤ token budget 的块，和 decode 混批；序列留在 RUNNING（已准入、KV 块已分配），只是 num_computed_tokens < prompt_len，不回 WAITING；代价是长请求 TTFT 略升。nano-vllm 没实现，vLLM 有。

## C. KV 与内存
### 9. PagedAttention 解决什么碎片问题？block table 怎么映射？  
答：PagedAttention 将 KV cache 分为固定大小的块，并将逻辑块映射到物理块，物理块不一定连续存储。申请内存时按需分配，从而减少内存碎片。补：解决的是外部碎片，最后一块的内部碎片仍在；block_table 管"读"，slot_mapping 管"写"。
### 10. KV 容量公式是什么？为什么 S2 是 310、S4 是 300？    
答：KV_capacity = total * gpu_memory_utilization - used - （peak - current）；block_bytes = 2 × layers × block_size × KV_heads × head_dim × dtype；num_kvcache_blocks = KV_capacity // block_bytes ；
used 是当前已使用的显存，peak 是历史峰值显存，current 是当前占用的显存。used/peak/current 每次进程启动都不同，而且 DEBUG/TEACHING 日志会抬高峰值。补：所以 310/300 都是当次预算的结果，块数不是常量。
### 11. block 的三态（ALLOCATE/REUSE/REACTIVATE）和引用计数；REUSE 与 REACTIVATE 的时序差别。——要点：块在 used 还是 free；ref_count +1 还是重置 1。
答：ALLOCATE：新分配块，ref_count=1；REUSE：命中已有的块，ref_count+1；REACTIVATE：之前被释放的块重新使用，ref_count 重置为 1。REUSE 是在块仍然在 used 状态下增加引用计数，而 REACTIVATE 是在块已经被释放到 free list 后重新激活。
### 12. prefix cache 为什么按 256 整块？链式 hash 为什么共享后缀无效？——要点：不满块 h=-1；hash 含 prefix。
答：按 256 整块是为了保证每个块的大小一致，便于管理和计算。链式 hash 共享后缀无效是因为 hash 值是基于整个前缀计算的，即使后缀相同，只要前缀不同，hash 值也会不同，从而导致无法命中缓存。

## D. 指标与性能
### 13. TTFT/TPOT 的定义、各自瓶颈，为什么必须分开看？  
答：TTFT（Time To First Token）是从请求发出到模型生成第一个 token 的时间，包含排队时间、prefill 时间和首 token 的生成时间。TPOT（Time Per Output Token）是模型稳态下生成每个 token 所需的时间。prefill主要受算力限制；TPOT在大模型下倾向于受带宽限制，batch 较小时，计算类似于多个向量乘矩阵，并行度低，偏向内存带宽受限，batch较大时，并行度高，偏向算力受限。所以两者要分开看。补：0.6B/3060、batch=8 时 AI≈4.35，脊点≈69，是访存侧；batch 8→64 每请求 TPOT 略升，但吞吐大升。
### 14. 为什么 TTFT ≠ prefill 时间？你 harness 里的 ttft_ms_p50 实际是什么？
答：TTFT 包含了排队时间、分词时间和采样时间，而 prefill 时间只包含模型处理输入的时间。harness 里的 ttft_ms_p50 是 ttft 的中位数。
### 15. 引擎的 num_tokens 不含 cached_tokens，会在哪两个方向骗你？
答：num_tokens 统计的是 prompt token 数 + 每条新生成的 1 个 token，完全没有扣掉 num_cached_tokens。
### 16. 吞吐、QPS、并发是什么关系？为什么 QPS 不能单独看？
答：吞吐量（Throughput）是单位时间内处理的 token 数，QPS（Queries Per Second）是单位时间内处理的请求数，并发是同时处理的请求数。QPS 不能单独看，因为它不考虑每个请求的输出长度，可能会误导性能评估，例如长 prompt 时时间花在 prefill 上，QPS 低估资源占用。吞吐量更能反映系统的实际处理能力，尤其是在处理长序列时。
## E. 分布式与边界（口述级）
### 17. TP 怎么切？切完多付什么通信？为什么多卡不线性加速？  
答：TP 是把一层内的矩阵按维度切开，每卡算一部分，行并行层再用 AllReduce 把部分和加起来。QKV 按头切（列并行，输出是分片，不通信），O 按输入维切（行并行，要 AllReduce）；MLP 的 gate_up 列并行、down 行并行，所以一层 2 次 AllReduce。不线性是因为通信在关键路径、每卡 GEMM 变小、跨 NVLink 域带宽骤降；TP 一般 ≤8，且要能整除 KV 头数（GQA 下 H_kv // TP 不能为 0）。
### 18. PD 分离的收益、成本、适用场景？  
答：prefill 算力密集、decode 访存密集且生命周期长，放一起会互相干扰（长 prefill 卡住 decode），TTFT/TPOT 没法独立优化。PD 分离把两阶段放两个池：P 算完把 KV 传给 D，各自扩缩。代价是 KV 传输：0.6B 每 token 112KB，8k≈900MB，200Gbps 要 37ms。判据是 KV 传输时间 / prefill 计算时间——大模型长 prompt 才划算，小模型短 prompt 往往净亏。
### 19. 引擎 vs 网关：超时、重试、取消、限流、缓存路由分别归谁？  
答：不全是网关。网关管接入与策略（超时、重试、限流、缓存路由），引擎管执行与状态（取消后停 decode、释放 KV block）；重试只在没出 token 前安全。详见 S6 六问。
### 20. cache-aware 路由什么条件下值得、什么条件下净亏？  
答：把共享前缀的请求路由到已有该前缀 KV 的实例。判据：从第 0 token 起逐块一致、至少满一个块（256）；收益 ≈ 256×满块数×(请求数−1)，第一个请求不省；长前缀的相对收益会下降（attention 仍要读 cached KV）。净亏场景：前缀 <256、低 QPS、路由造成热点/排队、缓存被淘汰；网关需要引擎暴露 prefix hash/命中率。
