# S3 参数消融

## 基线

注意：env.sh 末尾会 `cd $VLLM_WORKSPACE`（= vllm 仓库根），
所以 source 之后 cwd 一定是仓库根，脚本要用相对路径 learn-nano-vllm/example.py。

```
cd /media/bed8oy/3T/01_workspace/vllm
source ./env.sh

python learn-nano-vllm/example.py \
--model "$NANOVLLM_MODEL" \
--tp 1 \
--enforce-eager \
--max-tokens 16 \
--no-tqdm \
2>&1 | tee /tmp/baseline.log
```

| 参数 | 基线值 |
|---|---:|
| `kvcache_block_size` | `256` |
| `gpu_memory_utilization` | `0.9` |
| `max_num_batched_tokens` | `16384` |
| `max_num_seqs` | `512` |
| 并发数 | `128` |
## 实验
| 实验 | 改动 | 启动 | KV blocks | 显存峰值 | 实际 prefill tokens | 实际并发（decode 批） | TTFT | decode tok/s | OOM/等待 | 结论 |
|---|---|---|---:|---:|---:|---:|---:|---:|---|---|
| Baseline | 无 | 成功 | 310 | 10.05GiB | 39668 | 128 | 1455ms(p50) | 3979 | preempt=0 | 基准 |
| A | block `256→512` | 成功* | 155 | 10.05GiB | 43484 | 128 | 1465ms(p50) | 3393 | preempt=10，prefill 步 3→4，decode 步 127→161 | KV token 容量不变（155×512=310×256=79360），但块粒度变粗→块不足→抢占→decode −15%，且被抢占的序列要重 prefill，各步数都变多 |
| B | utilization `0.9→0.8` | 成功* | 268 | 8.90GiB | 44360 | 128 | 1467ms(p50) | 3361 | preempt=12，decode 步 127→161 | KV 容量 79360→68608（−13.6%），开始抢占，decode −16%；四个参数里最直观 |
| C | batched tokens `16384→8192` | 成功 | 317 | 10.02GiB | 39668 | 128 | 1107ms(p50) | 3939 | preempt=0，prefill 步 3→5 | prefill 分批更细，先入队那批 TTFT 更低（p90 不变），总吞吐基本不变 |
| D | max seqs `512→256` | 成功 | 310 | 10.05GiB | 36468 | 256 | 1351ms(p50) | 6143 | preempt=0 | 短 prompt（64–128）384 并发：decode 批被压到 256，聚合 decode 吞吐反而略升，p90 TTFT 4120ms |
| D-ctrl | max seqs `512`（对照） | 成功 | 310 | 10.05GiB | 36468 | 310 | 1351ms(p50) | 5295 | preempt=0 | decode 批 310，聚合吞吐略低；说明 3060 上 310 并发已过吞吐拐点 |

\* A、B 在原始代码上会崩，见文末「踩到的两个引擎 bug」。

> D 的第一版用长 prompt（128–512）+ 320 并发，结果 256 和 512 **完全一样**
> （都是 `max_decode_batch=188`、`preempt=99`）——因为 KV 块容量先把并发压到 188，
> `max_num_seqs` 根本没轮到生效。把 prompt 换短（64–128）让所有请求都能驻留后，差异才出来。
> 这是「参数要在它的生效区间里测」的实例。







## 跑前须知

### `max_num_batched_tokens` 有硬下限 4096

`Config.__post_init__` 里有：

```python
self.max_model_len = min(self.max_model_len, self.hf_config.max_position_embeddings)  # Qwen3-0.6B -> 4096
assert self.max_num_batched_tokens >= self.max_model_len
```

原因是 `scheduler.py` 没有 chunked prefill：它一次要么整个序列进 prefill，要么不进。
如果 budget 比单条序列还短，waiting 队头那条永远进不去，调度器会卡死。所以 C 只能测
`16384 → 8192`（或 `4096`），**不能低于 4096**。
### 关于 `max_num_seqs` 的语义坑

`scheduler.py` 里 `num_seqs` 是**本步**调度的序列计数，每步从 0 开始：

```python
num_seqs = 0
while self.waiting and num_seqs < self.max_num_seqs:   # prefill：本步最多收这么多
while self.running and num_seqs < self.max_num_seqs:   # decode：本步最多跑这么多
```

所以 `max_num_seqs` 限制的是**单步 batch 大小**，不是「常驻 running 序列总数」。
实测 `--max-num-seqs 256` 时 `max_running_seqs` 仍然能到 310（分多个 prefill 步陆续进来），
但每步 decode 批被稳稳定在 256。写实验结论时要看 `max_decode_batch`，不能看 running 长度。


## 两个引擎 bug

### bug 1：`can_append` 与 `may_append` 的块判定差一格 → B/D 直接 IndexError

`nanovllm/engine/block_manager.py`：

- `may_append()` 在 `len(seq) % block_size == 1` 时**真正分配新块**（回看它自己的注释
  「len % block_size == 1: 刚跨入新块 … 需要分配新 block」）；
- 但 `can_append()` 判断是否需要空闲块时用的是 `len(seq) % block_size == 0`。

结果：长度为 `k*block_size + 1` 的序列认为自己不需要块，`may_append` 却去取
`free_block_ids[0]` → `IndexError: deque index out of range`。
只要 KV 块紧张（`gpu_memory_utilization=0.8`、并发 > 块容量），decode 必崩。

已改为与 `may_append` 对齐：

```python
need_new_block = 1 if (len(seq) % self.block_size == 1) else 0
```
>上游没有这个bug，是教学版有问题！
### bug 2：`Sequence.block_size` 硬编码 256 → A（block 512）slot_mapping 对不上

`nanovllm/engine/sequence.py` 里 `block_size = 256` 是类级常量，
而 `ModelRunner` 用的是 `config.kvcache_block_size`。`Config` 只 assert `% 256 == 0`，
于是 `--kvcache-block-size 512` 能过校验，但 `Sequence.num_blocks / last_block_num_tokens`
按 256 算、`prepare_prefill` 按 512 展开 slot_mapping → 数量对不上：

```text
attention.py: store_kvcache  assert slot_mapping.numel() == N  → AssertionError
```

已在 `LLMEngine.__init__` 里加一行，让块粒度跟随 Config：

```python
Sequence.block_size = config.kvcache_block_size
```

> 上游 nano-vllm已经修改掉了这个bug。
