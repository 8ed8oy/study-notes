## 关键数字

- 权重：0.6B × 2B = 1.2GB（fp16）；KV：112KiB/token，seq=2048 → 235MB
- KV 块数：S2 310 / S4 300（当次预算，不是常量）
- prefix cache：共享 1024 前缀，TTFT 84ms → 32ms；saved 7168 token；192 token 前缀 saved 0
- 指标：TTFT 变 12.4×（401.5→32.3ms），TPOT 只变 1.05×（21.7–22.7ms），吞吐 115→336 tok/s
- 读缓存的代价：shared 冷启动比 short 冷启动慢 16.4ms（计算量同为 1536），差在 attend 7168 个 cached KV
- batch=8：AI≈4.35 FLOP/B，脊点≈69 → 访存侧；实测等效带宽 97GB/s（27%）
- 只有单卡 RTX 3060 12GB（`nvidia-smi` 实测 12288 MiB），所有多卡内容均为口述级

## 四个可讲结论

1. **指标口径陷阱**：引擎 `num_tokens` 不扣 `num_cached_tokens`；shared vs random 都报 8704，真实计算 1536 vs 8704（5.67×）；shared vs short 的 5.7× 是假的。
2. **prefix cache 边界**：256 整块、链式 hash；第一个请求不省；长前缀相对收益下降（attention 仍读 cached KV）；所以 cache-aware 路由不是无条件优化。
3. **引擎/网关边界**：状态归引擎、策略归网关、事实以引擎为准；取消要引擎释放 KV，重试只在未出 token 前安全，网关限流挡不住 OOM。
4. **多卡不线性**：TP 每层两次 AllReduce（O、down 之后，因为只有行并行出部分和）；TP ≤8 是 NVLink 域 + KV 头整除两条约束；PD 的判据是 KV 传输/prefill 计算——0.6B/8k/200Gbps 是 37ms vs 31ms，小模型不划算；prefix cache 的收益按命中占比 L/P 到 (L/P)² 缩水。
