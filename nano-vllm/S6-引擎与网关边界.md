# S6 引擎 / 网关边界（六问）

> 一句话：**状态归引擎，策略归网关，事实以引擎为准。**
> 用法：遮住答案讲，每题都要能说出「什么时候不成立」。

## 一、职责对照

| 功能维度 | Go 网关（集群控制面 / 分布式接入） | 推理引擎（单实例数据面 / 算力底座） |
| :--- | :--- | :--- |
| **流量与生命周期** | API 鉴权、配额流控、长连接汇聚（HTTP/gRPC/SSE）、请求取消广播 | Continuous Batching、Step 步进与自回归循环终止判断 |
| **状态感知与路由** | 全局 Prefix 路由（依据 Hash 路由到已有 Cache 的实例）、跨实例负载均衡 | 局部 Prefix Cache（RadixTree / Hash 维护本卡 Cache 命中与 Block 复用） |
| **内存与显存控制** | 集群实例水位感知（通过 Metric 跟踪各 Pod KV 满载率，避免打爆某卡） | 物理显存硬管理（PagedAttention、Block 申请/释放、Slot 映射、驱逐抢占） |
| **算力与模型执行** | 屏蔽多模型/多版本差异、模型冷热启动调度、实例弹性伸缩 | 硬件极限算力调度（GEMM/GEMV 算子融合、CUDA Graph、FlashAttention、TP/PP 通信） |
| **文本与编码处理** | 原始文本分词（高并发 CPU 预分词）、敏感词过滤、安全审查、模版拼装 | Token ID 数组接收、采样策略（Temperature/Top-P/LogitsProcessor）、Detokenize（部分集成） |

## 二、六问

**1. 请求取消时谁释放 KV cache？**

答：推理引擎。请求取消时（`r.Context().Done()` 或客户端发 cancel），Go 网关会把取消信号转给推理引擎，推理引擎在每个 step 结束时检查是否被取消，是则把 seq 从 running/waiting 摘掉、释放其占用的 block。

> 落到 nano-vllm：它没有 abort 路径，只有 EOS / max_tokens → FINISHED → deallocate（`vllm:learn-nano-vllm/nanovllm/engine/scheduler.py:220-235`）。要做取消，得让 aborted 走同一套收尾，否则 seq 一直留在 running、block 永不回收。

**2. 重试时谁保证不会重复生成？**

答：网关负责重试策略和幂等，引擎负责请求生命周期。每个用户请求应携带全局 request_id，重试必须携带相同 ID。引擎侧还得有一张 **idempotency 表**（id → 状态），否则同 ID 重试会再占一份 KV。已出 token 再重试 = 客户端收到重复前缀 + 重复计费；报错或 0 token 时才可重试。

**3. 如何限流防 OOM？**

答：网关按并发数、估算输入/输出 token 数、各实例 KV 使用率做**拒绝 / 排队 / 路由**（可用 Block 需引擎通过 metrics 暴露，网关侧只是近似的采样值）；推理引擎按显存水位与 Block 使用率做拒绝、排队、抢占或回收。

> 边界：限流只降低 OOM 概率，**不能保证**——OOM 的根因是 KV 预算与并发不匹配（`max_num_seqs` / `max_num_batched_tokens` 相对 KV 容量过大），兜底在引擎的 admission + preempt。按请求数限流会失灵：长 prompt 一个请求就能吃掉半个 KV 池，要按 token 预算限。

**4. TTFT 在哪测？**

答：网关测端到端 TTFT（排队 + 网络 + tokenize + prefill + 首 token 采样）；引擎测 `queue_time` 与 `prefill_time`。

> 口径：`TTFT − (queue + prefill + 首 token 采样) = 网络 + tokenize + 序列化`。引擎看不见排队前后的等待，所以 TTFT 永远以网关/客户端为准。

**5. 缓存 key 谁生成？**

答：这题的「key」至少指四样，先分清再答——请求 ID（网关发，只做标识）、**前缀路由 hash**（由内容派生，不是谁发的号）、KV block hash（引擎私有，链式含前缀、不满 256 为 -1）、会话 key（网关，只有 semantic cache 才需要）。

核心一句：prefix cache 是**内容寻址**，同样 token 序列必然同 key、不同内容必然不同，所以该问「谁**派生**、谁持有」。网关想自己算路由 hash 可以，但必须复刻引擎的 tokenizer、256 块、链式规则，少一样就永远不命中且不报错；更稳的是引擎暴露 prefix hash，网关只做路由决策。

**6. 请求状态和资源状态由谁作为最终事实？**

答：状态归引擎、策略归网关、事实以引擎为准。请求生命周期与资源占用（KV block、显存、并发槽）都以引擎为唯一事实源；网关只有代理视图——超时 / 重试 / 断连之后它看到的和实际经常对不上（网关记取消，引擎还在 decode）。网关的事实只到连接层：SSE 是否活着、已向客户端写出多少字节。

## 三、失败语义矩阵（六问串起来才看得见的坑）

| 组合 | 坑 | 谁兜底 |
|---|---|---|
| 超时 + 引擎仍在跑 | 网关已回 504，引擎继续 decode、继续占 KV | 网关超时必须带 cancel，引擎要能 abort |
| 取消 + 同 ID 重试 | 幂等表分不清「取消」和「失败」，重试被当重复 | 引擎状态区分 cancelled / failed |
| 限流 429 + 客户端自动重试 | 重试风暴放大负载 | 网关 retry budget + 429 带 Retry-After |
| SSE 中途断开 | 网关写失败，但没 cancel 上游 | 写失败立即 cancel |
| 多网关实例各自重试 | 同一请求投两次 | 幂等键必须在引擎侧生效 |

## 四、放哪边的三条判据

1. 需要**跨实例全局视图** → 网关（路由、配额、鉴权）；
2. 在**热路径上、每 token 都要做** → 引擎（batch、block 管理、采样）；
3. 状态**只在本进程内存里** → 引擎（KV block、seq 状态），网关最多读 metric。

## 五、30 秒口述

「边界三条：**状态归引擎，策略归网关，事实以引擎为准**。取消要引擎释放 KV，重试只在没出 token 前安全，限流挡不住 OOM——OOM 是 KV 预算的事，得引擎自己 admission + 抢占。TTFT 只能在网关测端到端，引擎只有 prefill 和排队时间；prefix hash 如果网关自己算，必须和引擎的 tokenizer、块大小、链式规则完全一致，否则永远不命中，还不报错。」
