# 网络安全与密码学
网络安全四大目标：
1. **机密性（Confidentiality）**：仅发送方和指定接收方能够理解报文内容。
2. **报文完整性（Message Integrity）**：确保报文内容在传输中未被篡改或替换。
3. **端点鉴别（End-point Authentication）**：确认通信实体的真实身份。
4. **运行安全性（Operational Security）**：防火墙、入侵检测系统（IDS/IPS）等系统防御。
## 1. 基础密码学原语

### (1) 对称密钥密码（Symmetric Key Cryptography）
- **核心概念**：通信双方共享同一个密钥 $K_S$。加密与解密互逆：$m = K_S(K_S(m))$。
- **分组密码（Block Ciphers）**：
    - **AES（高级加密标准）**：128/192/256 位密钥，分组长度 128 位，当前业界标准。     
    - **工作模式**：
	    - **ECB（电子密码本）**：同一明文块映射到相同密文块，无法隐藏数据模式。 
        - **CBC（密码块链接）**：使用初始向量（$\text{IV}$），每个明文块在加密前与前一个密文块异或，避免特征暴露。
- **特点**：运算效率极高，适合海量数据传输，但密钥分发是核心痛点。

### (2) 非对称/公开密钥密码（Public Key Cryptography）
- **核心概念**：每个实体拥有一对密钥：公钥 $K^+$（公开）与私钥 $K^-$（严密保管）。
    - 满足数学性质：$m = K^-(K^+(m))$ 且 $m = K^+(K^-(m))$。
- **代表算法**：**RSA**。
    - 原理：依赖于大整数分解的单向陷门函数。
    - 算法简述：
        1. 选择两个大素数 $p, q$，计算模数 $n = pq$ 及欧拉函数 $z = (p-1)(q-1)$。
        2. 选择与 $z$ 互质的加密指数 $e$。            
        3. 计算解密指数 $d$，满足 $ed \equiv 1 \pmod z$。
        4. 公钥为 $(n, e)$，私钥为 $(n, d)$。
- **特点**：解决了密钥安全分发问题，但计算开销极大（较对称加密慢数百至数千倍）。
### (3) 散列函数与报文鉴别码（Hash & MAC）
- **密码散列函数（Hash）**：具有单向性和强/弱抗碰撞性（如 SHA-256）。
- **报文鉴别码（MAC）**：基于共享密钥 $s$ 生成：$\text{MAC} = H(m + s)$，接收方重新计算比对即可检验真实性与完整性。

## 2. 为什么需要可信第三方（TTP）？
在开放分布式网络中，Alice 和 Bob 互不相识，直接通信会面临两大根源性威胁：
1. **对称加密的“**$N^2$ **爆炸”难题**：
    - 若网络中有 $N$ 个用户两两建立独立通信，需要维护 $\frac{N(N-1)}{2}$ 个对称密钥。当 $N$ 极大时，密钥分发与存储不可承受。
2. **非对称公钥体制的“中间人攻击（MITM）”**：
    - Trudy 可以在 Alice 和 Bob 之间截获公钥。Trudy 将自己的公钥 $K_T^+$ 冒充为 Bob 的公钥发给 Alice，再将自己的公钥冒充为 Alice 的发给 Bob。Alice 加密的消息实际上能被 Trudy 轻易解密。
    - **核心缺陷**：公钥本身不携带身份防伪证明。
为了解决上述问题，必须引入**可信第三方（Trusted Third Party, TTP）**：
- 在对称加密中：引入 **KDC（密钥分发中心）**。
- 在非对称加密中：引入 **CA（认证中心）** 与 **PKI（公钥基础设施）**。

## 3. 对称密码体系的可信第三方：KDC 与 Kerberos
### (1) 密钥分发中心（Key Distribution Center, KDC）
- **原理**：中央服务器 KDC 受到所有网络节点绝对信任。网络中每个用户只需与 KDC 预共享**一个唯一的长期主密钥**。
    - Alice 的主密钥：$K_{A\text{-KDC}}$
    - Bob 的主密钥：$K_{B\text{-KDC}}$
    - 全网密钥总数从 $O(N^2)$ 降低到 $O(N)$。
### (2) 经典的 KDC 认证与一次性会话密钥分发流程（Needham-Schroeder 模式）

```
     [Alice]                      [KDC]                      [Bob]
        │                           │                          │
        │ 1. 请求与 Bob 通信        │                          │
        ├──────────────────────────>│                          │
        │                           │                          │
        │ 2. 返回 Ticket 与 Ks      │                          │
        │<──────────────────────────┤                          │
        │                           │                          │
        │ 3. 发送 Ticket 给 Bob     │                          │
        ├─────────────────────────────────────────────────────>│
        │                                                      │
        │ 4. 使用临时会话密钥 Ks 进行加密通信                  │
        │<====================================================>│
```

1. **请求**：Alice 向 KDC 发送明文请求，表明希望与 Bob 建立安全连接，附带随机数 $R_1$（Nonce，防重放）。    
2. **KDC 生成会话密钥**：
    - KDC 随机生成一次性**会话密钥（Session Key）**$K_S$。
    - 为 Bob 制作一份**票据（Ticket to Bob）**：用 Bob 与 KDC 的共享密钥加密：$\text{Ticket} = K_{B\text{-KDC}}(K_S, \text{Alice})$。
    - KDC 将 $K_S$ 和 Ticket 一起用 Alice 的共享密钥加密发回：$K_{A\text{-KDC}}(K_S, R_1, \text{Ticket})$。
3. **Alice 解密与转发**：
    - Alice 用自己的主密钥 $K_{A\text{-KDC}}$ 解密，得到本次会话密钥 $K_S$ 以及她无法解开的 $\text{Ticket}$。
    - Alice 将 $\text{Ticket}$ 直接转发给 Bob。
4. **Bob 解密并建连**：
    - Bob 用 $K_{B\text{-KDC}}$ 解密该票据，取得 $K_S$ 并确认请求方确为 Alice。
    - 随后 Alice 与 Bob 即可使用 $K_S$ 进行高效的对称加密通信。
5. **典型实现**：**Kerberos 协议**（广泛用于 Windows Active Directory 域认证中，增加了票据授予服务器 TGS 的设计）。
    

## 4. 非对称密码体系的可信第三方：CA 与 PKI 信任链
### (1) 认证中心（Certification Authority, CA）
- CA 是网络公钥体系中的核心 TTP，负责审核实体的身份并为其签署**数字证书（Digital Certificate）**。
- **数字证书的本质**：将某个实体的真实身份信息（如域名、公司名称、有效期）与其实体公钥绑定，并附带 CA 的数字签名。
### (2) 证书签发与验证机制
```
【证书签发阶段】（Bob 与 CA 交互，线下/自动化）
 Bob 身份信息 + Bob公钥 Kb+ ──> Hash ──> [CA私钥 Kca- 加密] ──> CA数字签名
                                                            │
 完整证书 = (Bob 身份信息 + Bob公钥 Kb+ + CA数字签名) <───────┘

【证书验证阶段】（Alice 收到 Bob 的证书后）
 1. 提取证书中的明文公钥与身份信息 ──> Hash ──> 计算得到 Hash_1
 2. 提取 CA数字签名 ──> [CA公钥 Kca+ 解密] ───> 恢复出 Hash_2
 3. 对比 Hash_1 == Hash_2？ 
    └─ 若相等，证明 Bob 的公钥未被篡改，确属 Bob 本人！
```
### (3) PKI 信任链与根证书（Root CA）
- 实际网络中不是所有证书都由同一个 CA 签发，而是采用**树状信任链层次结构**：
    $$\text{Root CA} \longrightarrow \text{Intermediate CA (中间CA)} \longrightarrow \text{Server/Leaf Certificate (服务器证书)}$$
- **如何信任根 CA？**
    - 操作系统（Windows/macOS/Linux）和浏览器（Chrome/Firefox）在出厂安装时，内部已经预置了全球知名根认证机构的自签名根证书（内置了 **根 CA 的公钥** $K_{\text{RootCA}}^+$）。
    - 终端从服务器证书向上逐级回溯解密验证签名，直到命中系统信任库中的根 CA。

## 5. 综合实战：包含 TTP 验证的端到端混合安全传输全流程
本流程还原了 **现代安全协议（如 HTTPS / TLS 握手与数据传输）** 的经典综合交互模式：
### 角色准备
- **Alice（客户端）**：持有受信任 CA 的根公钥 $K_{\text{CA}}^+$。
- **Bob（服务端）**：拥有自己的公钥 $K_B^+$、私钥 $K_B^-$，以及由 CA 签发的数字证书 $\text{Cert}_B$。
- **CA（可信第三方）**：已向 Bob 颁发证书。
```
Alice (Client)                                                  Bob (Server)
    │                                                               │
    │ ── 1. ClientHello (支持算法套件、随机数 R_c) ──────────────> │
    │                                                               │
    │ <─ 2. ServerHello + 数字证书 Cert_B + 随机数 R_s ──────────── │
    │                                                               │
    ├─ 3. 验证证书 Cert_B (利用内置 CA 公钥 Kca+)                    │
    │     确认 Kb+ 属于 Bob                                         │
    │                                                               │
    ├─ 4. 生成预主密钥 PMS，用 Bob 公钥加密:                        │
    │     C_pms = Kb+(PMS)                                          │
    │                                                               │
    │ ── 5. ClientKeyExchange: 发送 C_pms ────────────────────────> │
    │                                                               │
    │                                6. Bob 用私钥解密:             │
    │                                   PMS = Kb-(C_pms)            │
    │                                                               │
    ├─ 7. 双方结合 R_c, R_s, PMS 本地独立派生会话密钥 Ks            ┤
    │                                                               │
    │ <================ 8. 使用 Ks 进行对称加密数据传输 ===========> │
    │   (加密: AES-GCM 或 AES-CBC + HMAC 防重放与防篡改)            │
```
### 流程分步详解
1. **协商与身份出示**：
    - Alice 向 Bob 发起连接，携带支持的加密套件与客户端不重数（随机数 $R_c$）。
    - Bob 响应，选定加密套件，回传服务端不重数 $R_s$，并发送自己的数字证书 $\text{Cert}_B$。
2. **可信第三方校验（打破中间人攻击）**：
    - Alice 使用本地内置的 $K_{\text{CA}}^+$ 验证 $\text{Cert}_B$ 上的 CA 数字签名。
    - 签名有效且证书域名、有效期无误后，Alice 安全提取出 Bob 的真实公钥 $K_B^+$。
3. **混合密钥交换**：
    - Alice 在本地生成高强度的预主密钥（Pre-Master Secret, $\text{PMS}$）。
    - Alice 用已验证合法的 Bob 公钥对 $\text{PMS}$ 加密：$C_{\text{PMS}} = K_B^+(\text{PMS})$，并发送给 Bob。
4. **解密与密钥派生**：
    - Bob 用只有自己持有的私钥 $K_B^-$ 解密密文，还原出 $\text{PMS} = K_B^-(C_{\text{PMS}})$。
    - 双方此时均掌握 $R_c$、$R_s$ 和 $\text{PMS}$，在本地通过伪随机函数（PRF）独立计算出完全相同的**对称会话密钥** $K_S$ 以及 MAC 密钥。
5. **高效安全通信**：
    - 握手结束，双方切换至对称加密（如 AES-256）传输报文主体，配合报文鉴别码（HMAC）或认证加密（AEAD）确保机密性与防篡改。
## 6. 分层协议映射总结

| 层次        | 代表协议               | 核心用途             | 密钥管理 / TTP 机制                        |
| --------- | ------------------ | ---------------- | ------------------------------------ |
| **应用层**   | **PGP / GPG**      | 安全电子邮件（离线机密性、签名） | **信任网（Web of Trust）**（去中心化互评，无中心 CA） |
| **应用层/域** | **Kerberos**       | 局域网单点登录鉴别        | **KDC（中央对称密钥中心）**                    |
| **传输层**   | **SSL / TLS**      | Web、API、邮件协议安全通道 | **CA 与 PKI 信任树**（中心化层级证书机制）          |
| **网络层**   | **IPsec (ESP/AH)** | 主机到主机、站点到站点 VPN  | **IKE（因特网密钥交换）**，预共享密钥或 PKI 证书       |
