# 一屏实验卡｜TCP 三次握手与 SYN 黑洞

> 一张卡回答一个问题。格式固定：**问题 → 操作 → 观察 → 解释 → 结论**（问题、操作、观察、解释、结论五段必须齐），另加一条"我事先预测了什么"用来防止事后诸葛亮。

## 0. 一句话结论

**`SYN` 发出去没有 `SYN-ACK`，和收到 `RST`，是两种完全不同的故障**：前者说明包在途中被静默丢弃（路由不可达/中间设备过滤/对端已下线，发送方无法区分），后者说明对端可达但端口没在监听；而且 SYN 黑洞不会快速失败，内核按指数退避重传（`tcp_syn_retries=6`），所以应用层看到的是"卡住很久后超时"。

## 1. 实验元信息

| 项 | 值 |
|---|---|
| 环境 | 本机 Ubuntu，物理网卡 `enp6s0`，TUN 代理（mihomo / Clash 内核）在旁 |
| 工具 | `tcpdump`、`ss`、`ip route get`、`node`（TLS 客户端） |
| 对象 | 机场入口 `sg02.333210.best:40000`（AWS 新加坡段，见排错卡）；对照 `baidu.com:443` 直连 |
| 关键数字 | 拨号超时 5.000s；`Flags [S]` 零回复；另一入口 `47.131.248.243` 正常 |

## 2. 问题（我要解释什么）

同一个客户端，`curl` 能通、Node/Edge 不通，十几分钟自愈。我想确认：**故障到底发生在"连代理服务器"这一跳，还是在后面的 TLS/HTTP**？

## 3. 我事先的预测（可证伪的预言）

> 如果故障在"本机 → 机场入口"这一跳的三次握手，那么：
> - 在**物理网卡**上应该能看到去往该入口 IP 的 `SYN`（`Flags [S]`）；
> - 而且**看不到**对应的 `SYN-ACK`（`Flags [S.]`）；
> - 同时，**直连**的对照连接（百度）应当正常；
> - 应用层错误应该在 mihomo 的**拨号（dial）**阶段就报错，而不是 TLS 握手阶段。

## 4. 操作（命令）

```bash
# 1) 代理自己的日志：故障发生在拨号还是 TLS？
journalctl -u mihomo -f | grep -E 'dial|error'

# 2) 物理网卡抓包，只看该入口 IP 的握手（-n 不做 DNS 反查，-S 显示绝对序号）
sudo tcpdump -ni enp6s0 'host 52.74.157.97 and tcp port 40000' -S

# 3) 对照：直连百度
curl -s -o /dev/null -w '%{http_code} %{time_total}\n' https://www.baidu.com

# 4) 连接状态与路由决策
ss -tanp | grep 40000
ip route get 52.74.157.97
```

## 5. 观察（原始输出，尽量贴原文）

mihomo 日志：
```
[TCP] dial 宝贝云 --> github.com:443
      error: sg02.333210.best:40000 connect error: context canceled
```

tcpdump：
```
<内网主机>.47680 > 52.74.157.97.40000: Flags [S]     ← 反复重传，零回复
<内网主机>.47696 > 52.74.157.97.40000: Flags [S]
...
47.131.248.243.40000 > <内网主机>.42392: Flags [P.], length 809   ← 另一条入口正常
```

配对探针（同一秒测四条路径）：
```
本机 23:50:13  small_curl=000@5.0018s  big_node=ECONNRESET@5022  mixed=000@5.0005s  baidu=200
```

## 6. 解释（机制）

1. **`Flags [S]` 没有 `[S.]`**：三次握手第一步发出去了、第二步没回来。区别对待：
   - 收到 `RST` ＝ 对端可达、端口没人听（主动拒绝）；
   - **零回复 ＝ 黑洞**：可能是路由不可达、中间设备丢弃、或对端机器已下线。**这三种从发送方完全无法区分**，因为 TCP 自身没有任何"在哪一跳被丢"的反馈机制（只有 IP 层的 ICMP 能报，而 ICMP 常被过滤）。
2. **为什么不是快速失败**：内核会对 SYN 做重传，退避序列 1/2/4/8/16/32s（`tcp_syn_retries=6`），所以表现是"卡很久"；而 mihomo 自己有 5s 拨号超时，所以应用层看到的是 `000@5.0000s` 这种**整数秒**——**精确到毫秒的整秒是软件定时器的指纹，不是网络时延**。
3. **为什么"连不上代理"和"TLS 失败"要分开**：`connect error: context canceled` 已经说明请求在 **dial 阶段**被取消，根本没进 TLS；如果错在 TLS，日志里会出现在 `dial` 之后的握手错误，抓包里也会看到 `SYN-ACK` 之后的 `ClientHello`。
4. **对照为什么关键**：四条路径（小包/大包/`mixed`/TUN）同时失败、只有直连百度活着 ⇒ 共模推断，故障点在所有这些路径的**共同上游**（本机到机场入口这一段），而不是包大小、入站路径或客户端实现。
5. **为什么时好时坏**：入口是一组轮询 A 记录，其中一部分地址已是黑洞；抽到好地址就通。详见排错卡的根因一。

## 7. 结论（可复述的一句话 + 可迁移动作）

- 结论：**看到 SYN 零回复，先怀疑"到某个具体目的 IP 不可达"，而不是应用层协议问题；先拿对照路径确认故障段落。**
- 可迁移动作：
  1. 任何"连得上/连不上"的问题，先 `tcpdump` 看握手三行，再谈 TLS；
  2. 永远同时测一条**直连对照**；
  3. 看到精确整秒失败，查软件超时定时器，不要往网络时延上想。

## 8. 常见追问（预演）

- **为什么抓包看不到 `SYN-ACK`，但 `ss` 里连接状态是 `SYN-SENT`？**——`ss` 反映本机内核状态，`SYN-SENT` 就是"发了 SYN 等回复"，两者一致。
- **怎么区分"对端机器死了"和"中间被墙/被过滤"？**——做 `traceroute`/`mtr` 看断在第几跳、换一台网络测同一 IP（异地/手机热点）。仍可能区分不了，此时只能说"黑洞"，不要说"被墙"。
- **TCP 重传要看什么？**——`tcp_syn_retries`、`tcp_synack_retries`，抓包里的重传间隔（1s/2s/4s…）。
- **如果我要证明是某条 `ip rule` 把包导错了呢？**——`ip route get <IP> from <src>`，看它选的是哪张表、哪个 dev。
