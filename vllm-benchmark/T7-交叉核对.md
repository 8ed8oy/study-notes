## 2. 交叉核对结果

| 口径 | 结论 |
|---|---|
| `/metrics` **均值**（`_sum/_count`） | **可用**。四组与客户端差 1.9–3.6ms（中位 2.7ms），不随 TTFT 变化 → 客户端 = 服务端 + 约 2.7ms |
| `/metrics` **分位数** | **不可用**。桶宽 20–2500ms，相对误差 15–50%，且不随尺度改善 |
| `/metrics` **计数器** | **精确**。prompt_tokens 5994 / generation 2816 / success 22 / preemptions 0 全部对得上 |
| `request_prefill_time_seconds`、`request_queue_time_seconds` | **完全失效**。最小桶 0.3s，237 条全挤在第一个桶 |

## 3. /metrics P50不可信

理由是它的桶边界：在 10–100ms 区间桶宽 20ms，出了这个区间就变成 150–2500ms。我要分辨的差异是 8ms（17.22 vs 25.08），而桶的宽度是它的 2.5 倍——**这个指标无法精确反应P50**。

更关键的是：**桶宽是绝对值，不会随请求变慢而等比缩小**。所以「线上 TTFT 大了，误差就不重要了」这句话是错的——TTFT 到 1.5 秒时桶宽 1500ms，相对误差依然是 100%。

我信它的是另外三样东西：均值的 `_sum/_count`、三个计数器的增量、以及「P50 落在哪个桶」这种量级判断。

至于我自己的客户端数字，我也不认为它是绝对真值——它比服务端高约 2.7ms，那部分是我自己拿连接、序列化、解析的开销。我报数时会说明这是**客户端侧 TTFT**。

## 4. 那 `/metrics` 的 P50 到底能干什么

不能用来说「TTFT 是多少」，但能用在四件事上：

| 用途 | 怎么用 | 为什么可信 |
|---|---|---|
| **量级分诊** | 先看 P50 落在哪个桶（十几毫秒 / 几十 / 几百） | 桶内具体值不可信，但「跨桶」这件事 100% 可信 |
| **回归报警** | P50 从 20ms 桶跳到 40ms 桶 → 有东西变了 | 跳桶是离散事件，不受插值误差影响 |
| **跨版本粗对比** | 两版用同一套桶，只看方向 | 桶一样，偏差同号，差异仍可辨 |
| **定 SLO 阈值的输入** | 先粗看量级，再决定阈值放 250ms 还是 500ms | 0.25 / 0.5 / 1.0 / 2.5 正好是桶边界 |

**反过来，它不能用在：**

1. 报告精确值（「P50 = 61.62ms」是对桶做线性插值造出来的，不是测出来的）。
2. 分辨 5–10ms 的 A/B 差异。
3. 跨实例比分布（桶相同，但两个实例的样本落点不同，插值误差方向也不同）。

**正确的汇报写法**：不给数，给区间——「TTFT P50 落在 **60–80ms** 桶」。这句话是诚实的，而且够用。

## 5. 遗留

- 「客户端 = 服务端 + 2.7ms」目前只有四组、各 22 条支撑；要当定论还缺跨 prompt 长度的复核。
- `_sum/_count` 只给均值，给不了分位数。要分位数只能用自己的客户端。
