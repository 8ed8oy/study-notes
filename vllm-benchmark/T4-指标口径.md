# T4 指标口径

## 0. 术语表（先看这个，再看下面的表）

| 词 | 意思 |
|---|---|
| prefill | 一次性处理整个 prompt 的阶段，算力密集 |
| decode | 逐 token 生成的阶段，显存带宽密集 |
| TTFT | Time To First Token，发出请求 → 收到第一个输出 token |
| TPOT | Time Per Output Token，解码总时长 ÷ 输出 token 数 |
| ITL | Inter-Token Latency，相邻两个 token 的间隔；TPOT 是它的平均值 |
| SSE | Server-Sent Events，流式协议；每帧一行 `data: {...}`，结束发 `data: [DONE]` |
| `usage.completion_tokens` | 服务端自报的输出 token 数，比数帧数准 |
| histogram `_bucket` / `_sum` / `_count` | Prometheus 直方图三件套：分桶累计计数 / 总和 / 总次数 |
| `_total` | 单调递增的计数器，算吞吐要取两次抓值的差 |
| KV cache / prefix cache | 已算过的注意力缓存；同样的前缀第二次来能跳过 prefill |
| warmup | 不计入统计的预热请求 |
| P95 | 分位数，95% 的样本小于等于这个值 |

## 1. 四个指标的定义

| 指标         | 我的定义（一句话 + 公式）                |
| ---------- | ----------------------------- |
| TTFT       | 用户从发送到看到第一个token的时间           |
| TPOT / ITL | prefill完成后每decode出一个token所需时间 |
| tokens/s   | 每秒decode产生的token数             |
| 成功率        | 返回token的条数/总发出条数              |

## 2. 计时

| 项                                               | 我的选择                  | 理由                                                                       |
| ----------------------------------------------- | --------------------- | ------------------------------------------------------------------------ |
| 时钟源（`time.perf_counter` / `time.time` / 服务端时间戳） | `time.perf_counter()` | 单调不回退、纳秒精度，同进程内做减法不需对时；`/metrics` 只给时长（`_sum`/`_count`）不给绝对时间戳，服务端这条路走不通 |
| 起点（发出请求 / TCP 建连完成 / 首字节到达）                     | 发出请求                  | 连接已复用，没有握手；起点 = 写请求前一刻                                                   |
| 终点（首帧 / 首个非空 delta / 首字节）                       | 首个非空delta             | chat 首帧是 role-only，`content` 为空，不带字；首字节测的是 RTT 不是模型速度                    |
| 是否复用连接（keep-alive）                              | 是                     | 排除 TCP/TLS 握手，否则 c=4 时 TTFT 被网络抖动主导                                      |
| 客户端与服务端指标谁为准                                    | 客户端                   | 用于要回答用户等多久                                                               |

## 3. 样本

| 项                                  | 我的选择                                                                               |
| ---------------------------------- | ---------------------------------------------------------------------------------- |
| warmup 几条、怎么排除                     | 2 条，参数与正式一致（同 prompt、同 `max_tokens`）；结果写进 JSONL 但打 `phase=warmup` 标签，统计时按标签过滤，不删记录 |
| 每组多少条                              | 20 条（warmup 另算，共 22 次请求）。n=20 是 P95 有意义的下限                                         |
| 分位数怎么算（排序取位 / numpy percentile 插值） | `numpy.percentile(method="linear")`，报告注明 n=20；n=20 时 P99 等于 max，不报                 |
| 并发怎么实现（线程 / asyncio / 多进程）         | 线程                                                                                 |

## 4. 失败与边界

| 场景          | 怎么记          |
| ----------- | ------------ |
| HTTP 非 200  | 记录错误码和报错核关键字 |
| 连接超时        | `status=timeout`，阈值 connect=5s / read=60s；计失败，保留在 JSONL |
| 流中断（收到一半断连） | `status=truncated`，保留已收 token 数 + t_first/t_last；**只进成功率分母，不进 TTFT/TPOT 统计**（半截算 TPOT 会偏低） |
| 重试          | 正式样本不重试。重试会掩盖服务端不稳定；若必须重试，加 `attempt` 字段并在报告里分开报 |

## 5. 与服务端指标的对应

| 客户端指标    | `/metrics` 里对应什么 | 预期差异 |
| -------- | ---------------- | ---- |
| TTFT     | `vllm:time_to_first_token_seconds`（histogram，`_sum`/`_count` 得均值） | 客户端 ≥ 服务端；差值 = 网络 + SSE 传输 + 客户端解析，本机回环应在个位数 ms |
| TPOT     | `vllm:inter_token_latency_seconds`（逐 token 间隔） | 与 `(t_last−t_first)/(n−1)` 同义。注意 `vllm:request_time_per_output_token_seconds` 是每请求解码均值，分母不同，别混用 |
| tokens/s | `vllm:generation_tokens_total` 两次抓取的差分 ÷ 时间差 | 服务端略高：客户端只算到最后 token 到达，尾部有残差 |
| 成功率（补充）  | `vllm:request_success_total`（按 `finished_reason` 分）+ `vllm:num_preemptions_total` | 客户端 ≤ 服务端：客户端含网络失败，服务端只看见到达的请求 |

> 指标名取自 `vllm:logs/bench/probe/08_metrics.txt`。

## 6. 一句话

> 「客户端用 `perf_counter` 在发请求前记 t0，在第一个 `delta.content` 非空的 SSE 帧记 t1，TTFT = t1 − t0。连接复用排除握手，warmup 2 条不计，20 条取 P95。服务端的 `vllm:time_to_first_token_seconds` 只用来交叉验证，差值就是网络 + SSE 传输开销。」

> 补充：TPOT = `(t_last − t_first) / (completion_tokens − 1)`，分母取 `usage.completion_tokens`，不取帧数（chat 帧数与 token 数不等）。
> 吞吐分两个数：单请求 `completion_tokens / (t_last − t_first)`；系统吞吐 `Σ completion_tokens / 墙钟时间`。报告里写哪个必须说明。
