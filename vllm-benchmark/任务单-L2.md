## 0. 为什么是 6 h 不是 14 h

三条都成立，才允许砍：

1. **L2 的产出是「两张图」，不是「矩阵全覆盖」。** 计划 §4.1 的 `并发 × 短中长 × 输出 64/256 × cache 开关` 是**手段**；两轴曲线才是交付物。c=1/4 已有（[T6-主实验](vllm-benchmark/T6-主实验.md)），补 c=8/16/32 就能画出单调段和拐点。
2. **L3 的钱已经付过一半。** [T8-L1收口](vllm-benchmark/T8-L1收口.md) §5 留着十条异常，其中至少四条是现成的失效样本。L3 的活主要是**整理成能口述的一页**，不是重做实验。
3. **砍掉的项要写进报告「未覆盖 + 原因」。** 这是诚实，不是偷工；计划 §4.1 本来就写「不追 5—10 页」。

## 1. 任务表

### T9 并发扫描：找拐点（2 h）

目的：把 c=1/4 两个点扩成一条曲线，回答「3060 + Qwen3-0.6B + 272-token 请求，饱和点在哪」。

**命令 = `vllm:README.md` §3 那条，只改 `--concurrency` / `--num-requests` / `--label`。**
`--prefix` 必须原样保留 `r0-1794459251123456789`——它 21 token，加 p1 的 251 才等于 272；换掉就和 T6 不可比。

```bash
cd <vllm 仓库根> && source "$VENV/bin/activate"    # VENV 见 vllm:README.md §1

for c in 8 16 32; do
  python bench/bench.py \
    --concurrency $c --num-requests 32 --warmup 2 \
    --prompt-file bench/prompts/p1-retrieval.txt \
    --prefix "r0-1794459251123456789" \
    --label "T9-c$c"
done
```

- `--num-requests 32`：c=32 时若只用 20 条，实际并发只有 20。三组统一 32 条，样本量一致
- 与 T6 的 n=20 不同，报告里要标样本量；P50 仍可比
- 可加一组 `--concurrency 4 --num-requests 32 --label T9-c4`，和 T6-hot-c4（25.08 ms）对照，当一致性检查

**产出**：`T9-c8/16/32-<stamp>.jsonl` + 各组 metrics 前后快照（bench.py 自动存）。
**验收**：五个点（1/4/8/16/32）的 TTFT P50 与系统 tok/s 都有数，且能指出曲线在哪一段变平。

**跑之前的预判（跑完对照，写进 T9 笔记）**：

- c=1→4 已经 ×2.94，c=8/16 大概率继续接近线性，拐点在 16 之后，或者根本没有；
- **c=32 不拐也是结论**：「本机 400-token 请求下饱和点 > 32；瓶颈不是 KV（32×400 = 12800 ≪ 81072），是单卡算力」。
- **不许**为了「测出拐点」去调 `max-num-seqs` 硬凑。

### T10 prefix cache 关：对照组（1.5 h）

目的：计划 §4「必须完成」第 4 条；同时给 2027 年网关 v1 的 cache-aware routing 留 baseline。

1. `vllm:bench/serve.sh` 的 `vllm serve` 里加一行 `--no-enable-prefix-caching \`（0.31.0 已确认有 `--no-` 形式）
2. `pkill -f "vllm serve"`，等 3 s，`bash bench/serve.sh`，`curl /v1/models` 自检
3. **先确认真的关了**：`curl -s :8000/metrics | grep -E "prefix_cache_(hits|queries)_total"`，跑完两组后 `hits` 应几乎不涨（T6 那组是涨的）
4. 跑 c=1 / c=4 各 20 条，命令同 T9 只改 label
5. **跑完把 serve.sh 改回去并重启**，否则后面所有实验都在无缓存态

**产出**：`T10-nocache-c1/c4-<stamp>.jsonl`
**验收**：算出两个数——**Δ TTFT（命中 vs 不命中）** 与 **Δ 系统吞吐**。

## 2. 固定条件（中途不改）

| 项 | 值 |
|---|---|
| model / dtype / max-model-len / gpu-mem | Qwen3-0.6B / float16 / 4096 / 0.90 |
| prompt | `vllm:bench/prompts/p1-retrieval.txt` + 固定前缀 `r0-1794459251123456789` = **272 token** |
| 输出 | 128（T11 排队样本例外时 512） |
| 采样 | `temperature=0`、`seed=0`、`ignore_eos=true` |
| warmup | 2 条不计，但保留在 JSONL |
| 样本 | T9 每组 32；T10 / T11 每组 20 |
| 分位 | `numpy.percentile(method="linear")`；n=20 不报 P99 |
| 计时 | `time.perf_counter()`，客户端为准，`/metrics` 交叉 |

## 3. 通过判据

1. c=1/4/8/16/32 五个点都有 TTFT P50 与系统 tok/s；
2. cache on/off 至少一组同条件对照；
3. 三个失效样本写成能口述的一页；
4. 3 页报告 + 2 张图；
5. 每个数指得回 JSONL。

## 4. 明确不做（报告里要写「未覆盖 + 原因」）

- 短/中/长输入三档 × 输出 64/256 的全矩阵 → 只做 272-token 一档
- 多模型对比
- P99（n=32 也不够）
- 报告超 3 页、图超 2 张
- 为凑「拐点」而调 `max-num-seqs` 等启动参数
