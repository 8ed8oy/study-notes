# T5 压测客户端 v0

> 代码：`vllm:bench/bench.py`（压测）、`vllm:bench/stat.py`（按 rid 打印单条）
> 口径：[T4-指标口径](vllm-benchmark/T4-指标口径.md)，这一页只记「怎么实现的 + 跑出了什么」
> 原始数据：`vllm:logs/bench/raw/*.jsonl`

## 1. 客户端做了什么

| 环节 | 实现 |
|---|---|
| 请求 | 流式（`stream=true`）+ `stream_options.include_usage=true`，否则拿不到 `usage` |
| 连接 | 每线程一个 `Session`，`pool_maxsize=并发数`，`max_retries=0` |
| 读流 | `iter_content(chunk_size=None)` 手动切 `\n`，不用 `iter_lines` |
| 起点 | `t_start = perf_counter()` 在 `session.post()` **之前** |
| 终点 | `t_first` = 第一个 `delta.content` / `text` **非空**帧的到达时刻 |
| 另记 | `t_first_frame` = 第一个 data 帧（chat 那帧是 role-only） |
| token 数 | 优先 `usage.completion_tokens`，兜底数非空片段 |
| 入队 | warmup 先入队，标 `phase=warmup`；正式标 `phase=measure` |
| 写盘 | 每请求一行 JSONL，加锁追加；首行是 `meta`（含全部参数与请求体） |
| 统计 | `summarize()` 跳过 `meta`、只收 `phase=measure`；`np.percentile(method="linear")` |

## 2. 六个自检题的正确答案

| # | 问题 | 答案 |
|---|---|---|
| 1 | `t0` 为什么记在 `post` 之前 | 记在之后会漏掉「取连接 + 写请求字节 + 等响应头」这段时间，TTFT 偏小。连接复用后不含握手 |
| 2 | 换 `iter_lines()` 会怎样 | 影响很小（回环上亚毫秒）。不用它的理由是**可控性**：它的缓冲语义不透明，出问题无法定位；自己读能保证时间戳记在字节到达那一刻 |
| 3 | 为什么取 `usage` 而不是数帧 | 帧数 ≠ token 数，因为**空帧**：chat 首帧 role-only、收尾帧带 `finish_reason`、usage 帧 `choices` 为空。**不是**「一帧多 token」 |
| 4 | 去掉 `if piece:` 会怎样 | role-only 首帧就占了 `t_first`，TTFT 被**低估** |
| 5 | 不设 `pool_maxsize` 压 c=16 | 默认上限 10，多出的请求**静默排队**，并发是假的，不报错 |
| 6 | `--warmup 0` 会不会污染 P95 | **会**。warmup 循环不执行 → 第一条的 `phase` 是 `measure` → 必然进样本 |

### Q6 的实测证据

`X1-p1-w0`（warmup=0）：`m0 = 33.78ms`，稳态 ≈16.5ms，是 2 倍。
P95 从 16.80 抬到 17.81（+6%）。

正确表述：**在本配置下 warmup 对 P95 影响仅 6%，因为 prompt 太短，冷启动代价本身不大。** 不是「warmup 没用」。

## 3. 结果

### 3.1 c=1 两组（prompt 固定、warmup 2、n=20）

| 组 | TTFT P50 | TTFT P95 | TPOT P50 | 单请求 tok/s | 系统吞吐 tok/s | 成功率 |
|---|---|---|---|---|---|---|
| completions（5 token） | 16.50 | 16.80 | 4.56 | 220.9 | 214.5 | 100% |
| chat（13 token） | 11.03 | 11.60 | 4.57 | 220.3 | 216.0 | 100% |

自洽性核对：`TTFT + 127×TPOT ≈ 墙钟/20`，`20×128=2560` 与 Σtokens 一致。

### 3.2 c=1 vs c=4

| 并发 | TTFT P50 | TTFT P95 | TPOT P50 | 系统吞吐 tok/s | 扩展效率 |
|---|---|---|---|---|---|
| 1 | 16.56 | 17.20 | 4.56 | 214.5 | — |
| 4 | 24.25 | 33.38 | 4.81 | 675.1 | **3.15×（79%）** |

解读：并发 4 倍，吞吐 3.15 倍；代价是 TTFT P50 +46%、P95 翻倍，TPOT +5%。
这是「吞吐 ↔ 延迟」取舍的第一手数据。

### 3.3 量级校验（心算，面试会问）

```
Qwen3-0.6B fp16 权重 = 0.6G × 2B = 1.2 GB
RTX 3060 带宽 ≈ 360 GB/s
batch=1 理论上限 = 360 / 1.2 = 300 tok/s → 实测 220，达 73%
batch=4 理论上限 = 1200 tok/s → 实测 675，达 56%
```

## 4. **发现**：TTFT 的双平台由「残余 token 数」决定

8 个点，全部落在这条规律上：**prefix cache 命中后，若残余未缓存 token 恰为 1 个，TTFT 走低平台；否则走高平台。**

| prompt token | 命中整块 | 残余 | TTFT | 路径推测 |
|---|---|---|---|---|
| 5 | 0 | 5 | 16.5 | eager prefill |
| **17** | 1 | **1** | **10.5** | **decode（CUDA graph）** |
| **18** | 1 | **2** | **16.34** | eager prefill（边界验证） |
| 20 | 1 | 4 | 16.0 | eager prefill |
| 23 | 1 | 7 | 16.9 | eager prefill |
| 27 | 1 | 11 | 16.96 | eager prefill |
| 31 | 1 | 15 | 16.82 | eager prefill |
| **33** | 2 | **1** | **10.84** | **decode（CUDA graph）** |
| 37 | 2 | 5 | 16.59 | eager prefill |

- 块大小 16 **不是猜测**，取自 `/metrics` 的 `vllm:cache_config_info`：
  `block_size="16"`、`effective_attention_block_size="16"`、`user_specified_block_size="False"`、`enable_prefix_caching="True"`
  （同处 `num_gpu_blocks="5067"`、`kv_cache_size_tokens="81072"`，`5067×16=81072` 自洽）
- 差值 ≈ 5.5ms，与 1 个 TPOT（4.57ms）同量级，支持「单 token 走 decode 步」的解释
- **决定性验证**：预测 33 token 也应落在低平台 → 实测 10.84ms，成立
- **全命中不会变成 0 残余**：272 token（= 17 块整数）在固定前缀、缓存全命中的情况下仍是 **17.63ms**（`ZP-smoke`）。说明引擎不会把整段命中的 prompt 压成 0～1 个待算 token，残余仍 > 1（推测取整到块边界，残余 16；未验证）。这条对 T6 有用：**hot 组不会意外掉进快平台**。
- **边界收窄（11/12 12:52 复跑）**：残余 **2** 个（18 token）仍在慢平台，P50 **16.34ms**（样本 16.45 / 16.34 / 16.49 / 15.96 / 16.05）。所以门槛是「**恰好 1**」。
  命令：`vllm:bench/bench.py --concurrency 1 --num-requests 5 --warmup 2 --label Z18 --prompt "id-<ts> word The capital of France is"`
  数据：`vllm:logs/bench/raw/Z18-20261112-125240.jsonl`

所以这条规律的准确表述是：**第一步要算的 token 数恰好为 1 时走快平台，> 1 时走慢平台**；`prompt_tokens` 只是它的间接指标。

这一条同时解释了之前所有反常现象：`id-<ts> The capital of France is` 恰好是 17 token，所以它 10.5ms；默认 prompt 5 token 无整块命中，所以每轮全量 prefill，16.5ms。

**边界**：本结论只在 prompt ≪ 触发 chunked prefill 的长度下成立；prompt 上千 token 时 prefill 计算量会盖过固定开销，规律应失效（未验证）。

## 5. 由这条发现得出的实验纪律

1. 短prompt下，**TTFT 主要测的是「固定开销 + 走哪条 code path」，不是 prefill 算力。** 5 token 和 37 token 一样慢。
2. 要测 prefill 能力，prompt 必须上千 token。
3. **T6 的所有对比组，prompt 必须逐字节相同。** 3 个 token 的差就能让 TTFT 变 60%，比并发的影响还大。
4. 报 TTFT 时必须同时报 `prompt_tokens`，否则数字无法比较。

## 6. 遗留

- 早期 JSONL（`X1`/`A`/`B`/`C`/`S*` 之前）没有 `prompt_tokens` 字段，是加字段前跑的；`S*` 及之后都有。
- 「残余恰好 1 token 走 decode」：**边界已实测确认**（17 低 / 18 高），但「走的是 CUDA graph 还是单 query attention kernel」是**行为推断**，没读源码。按硬边界不再深挖，留作 L3 候选。
- 历史遗留：同启动参数下 KV cache 79,088 vs 81,072（2.5%）差异仍未解释（11/12 重启后为 81,072）。
